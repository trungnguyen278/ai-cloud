# 0012 — What one device can exhaust: frames bounded below the session, connections cut once closed, handshakes counted once their token verifies, and reading bounded by length

- **Status:** Proposed. The owner has not agreed yet; the values are starting points, in `config/base.toml`.
- **Date:** 2026-11-21, revised 2026-11-22 after the two reviews of ai-cloud#32, and as the cloud link 3.4 bounds the frames

## Context

The cloud link says that each side limits what it takes from the other (Messages, Rates; SEC-15). Its session already does so for messages: `rate` a second, in bursts of `burst`, with `backlog` more waiting, and a connection to which nothing could be sent for two ping intervals ends `stalled` ([ADR-0011](0011-control-channels.md)). The rest was unbounded (research of 2026-11-12, and the reviews):

- **Frames below the session are no message.** uvicorn 0.54 handles each Ping, Pong and continuation frame as it parses it, below the application, so the session's rates never count them. websockets queues a Pong for each Ping, which uvicorn writes whether its transport takes more or not (`handle_ping`), and uvicorn keeps each fragment of a message until its last. On the real server (the review of 2026-11-22), a device with a valid token that sent empty Pongs, 6 bytes each, held a replica at 100 % of a core and another device's ping to pong from 2.5 ms to some 280 ms; one that sent Pings and read nothing grew its write buffer by 156 MB in 12 s; empty continuation frames grew uvicorn's list of fragments to 1.7 million in 6 s. HTTP/2 had the same floods: CVE-2019-9512, "Ping Flood", whose answers queue, and CVE-2019-9518, "Empty Frames Flood" (Netflix's advisory 2019-002). The cloud link bounds them since 3.4 (Messages, Frames).
- **A connection that is closed need not end.** uvicorn 0.54 closes a connection with its transport's `close`, on each of its ways to close one: after the closing handshake, after its own 10 s wait for the peer's close frame, when the application returns, and as the server stops (`websockets_sansio_impl.py`). asyncio's `close` then waits for what is buffered to leave ("buffered data will be flushed asynchronously", asyncio's Transports, docs.python.org/3.14). A device that reads nothing lets nothing leave, so its socket, its transport and what waits in it stay for ever. Nothing in uvicorn aborts a WebSocket on the sans-I/O path that it runs; its pull request 3230, "Add `--timeout-write`", would, and was still open on 2026-11-21 (last updated 2026-10-25; uvicorn 0.54.0 of 2026-09-25 is the latest release).
- **Nothing limits handshakes, and a limit counted before the token is anyone's to spend.** uvicorn's `limit_concurrency` answers 503 only to plain HTTP requests: an upgrade returns before the check (`h11_impl.py`, `httptools_impl.py`). Each handshake costs a token's signature, then a read of the registry, and one that opens replaces the device's older connection, with a hint to every replica. A count of every attempt, made before the token, is spent by whoever sends them: in the review, one client without a token, 619 handshakes a second, had the replica refuse real devices with it.
- **Reading costs as much as the text is long, and messages are counted, not their length.** Reading a frame of 1 MiB, the largest that the protocol allows, costs the event loop 11 ms for one long string, 108 ms for short strings or many names, 168 ms for empty arrays, 190 ms for small numbers; the schema then takes under 2 ms (`read_message` and `Schema.problem`, best of 5, Windows, 2026-11-21). At 50 messages a second, one device could hold a replica's event loop for most of each second; and a count kept by each connection starts whole, so ten connections of one device read ten bursts at once.
- **Each handshake writes lines.** uvicorn 0.54 logs every WebSocket handshake to `uvicorn.error` at INFO, whatever `access_log` says, and has websockets log one more there (`connection rejected (401 Unauthorized)`); and it logs an error for each refusal once the application returns, "ASGI callable returned without completing handshake", which its pull request 3138 fixes (merged 2026-10-25, in no release on 2026-11-22). A flood of handshakes wrote three lines for each. A request that uvicorn cannot parse, or asks to upgrade to what it does not serve, writes a warning there too, "Invalid HTTP request received." or "Unsupported upgrade request.", where nginx logs an invalid request at its info level, below its default (`ngx_http_request.c` and `ngx_log.c`, read 2026-11-22). A device's text that is no UTF-8 writes an error with its traceback, "Invalid UTF-8 sequence received from client.", and so does a frame that breaks WebSocket's rules before the handshake is answered, as asyncio's "Fatal error: protocol.data_received() call failed." (the second review).

The cloud link already tells a device what to do with a refused handshake: 429 means it connects too often, 503 that the cloud is busy, and after either it connects again after its backoff, "and no sooner than `Retry-After` if the answer has one" (The control channel, Refusals). Nothing here needs more on the wire.

## Decision

1. **Frames below the session keep the cloud link's Frames (since 3.4), and past them the connection closes with 1008,** the code of a message that "violates its policy" (RFC 6455, 7.4.1); the session ends `flooded`. A fragment under 1 KiB that is not its message's last closes it, "fragment too small", and so do Pings and unsolicited Pongs past one a second, with twice the link's `ping_interval` of them at once, 40 at the starting point, "too many pings". A Pong that answers the server's own Ping counts for nothing; the api sends none, so every Pong counts. Fragments of 1 KiB or more are a message as it comes, and pass: what they carry is paced as the session reads it, by `text_rate`, and bounded by `ws_max_size`: each fragment's header comes with 1 KiB or more of what the session reads, and a message holds 1024 of them at most. Two messages of 1 MiB in fragments of 1 KiB, back to back, are read. The values are the protocol's, so `entry/websocket.py` names them, and the Pings' allowance follows `[devices.link] ping_interval`, which the cloud's hello tells the device. It runs uvicorn's sans-I/O protocol but parses what comes 1 KiB at a time, and no further than the application has taken: uvicorn stops reading once a message waits for the application, but would parse the rest of a read of 256 KiB. In pieces of 1 KiB, 1 MiB takes 1.7 ms to parse in one frame and 3.8 ms in fragments of 1 KiB; in pieces of 256 KiB, 1.5 ms and 4.0 ms (websockets 17.3, best of 3, Windows 11, CPython 3.14, 2026-11-22). Only the latest Ping's Pong waits for a transport that takes no more, as RFC 6455 lets an endpoint answer (5.5.3). Envoy closes an HTTP/2 connection the same way, past `max_outbound_control_frames` (1000) or `max_consecutive_inbound_frames_with_empty_payload` (1) (its Http2ProtocolOptions, read 2026-11-22); AWS IoT Core processes "data received or sent over a client connection" at 512 KB a second (its quotas, read 2026-11-22), and EMQX's `bytes_rate` pauses a client's socket. The bound is the api's own: a developer's own cloud runs without [ADR-0004](0004-hosting.md)'s Cloudflare Tunnel, and nothing here relies on what is in front of the process.
2. **A connection that the api's server closes ends within `[api] ws_close_timeout`, read or not.** The protocol wraps the connection's transport: each `close` aborts it once `ws_close_timeout` has passed without the connection ending, and the closing handshake waits as long for the device's close frame, where uvicorn waits 10 s. Every way that uvicorn closes a connection goes through that one `close`, so none is missed. Every end of a device's connection spends up to `[devices.link] close_timeout` (5 s) on its bye and its close together: a session's, and those before a session is carried, a hello refused, a bye or another message before the hello, a hello that does not come within `hello_timeout`, and a reconnect before the session starts. Its connection then ends within twice `ws_close_timeout` (2 s): once for the device's close frame, once for what the device has not read. A device that reads nothing is so cut at most 9 s after its session ends, or its hello is refused, and a stop no longer waits for it.
3. **Each device may open its control channel `[devices.connection_rate]` times a period:** 10 at once, then one every 6 s, counted in Redis by `shared/rates.py`, as the token endpoint's rate is, for the device that the token names, once the token verifies, before any other count and before the registry is read. Past it, the handshake gets 429, with `Retry-After` in whole seconds; when Redis cannot count, 503 with none, so the device waits for its backoff, as it would for any 503 (presence needs Redis anyway). AWS IoT Core takes one CONNECT a second from each client ID, without bursts, and that quota cannot be raised (AWS IoT Core endpoints and quotas, read 2026-11-21); here a device's backoff, a new token and a replica that goes away make a few in a row.
4. **Each replica takes `[devices.link] connect_rate` connections a second from all devices together,** in bursts of `connect_burst` (100 and 200), counted in its own memory for each handshake whose token verified and that its device's own rate let through, before the registry is read. Past it, the handshake gets 503, with `Retry-After`. What it bounds is a storm of real devices, such as every device returning at once after a replica restarts, whose each handshake reads the registry and writes the presence. Brokers bound new connections per listener the same way: EMQX's `max_conn_rate` ("1000/s" in its example) pauses accepting them, and HiveMQ's `connect-rate` (500 a second, in bursts of twice that) disconnects new clients; Azure IoT Hub's S1 unit takes at least 100 new connections a second and answers 429 past them (research of 2026-11-12). The count is the replica's, not shared in Redis: what it protects is this replica.
5. **An attempt without a valid token spends nothing that the cloud counts, nor writes anything.** The token's signature is checked first, in this process, without I/O, so a host without a valid token never makes a device's handshake fail. Refusing such an attempt costs the replica 1.2 to 1.8 ms of a core, most of it to accept the connection, parse its request and answer, before the application runs: 1.2 to 1.4 ms with no token or one that is no JWT, 1.6 to 1.8 ms with a forged signature; a valid token past its device's rate costs 2.1 to 2.5 ms, with its round trip to Redis (400 attempts in a row of each, twice, server and client on one Windows 11 machine, CPython 3.14 and asyncio, 2026-11-22). The token's own check is 4 µs without a token and 260 µs for a forged ES256 signature (the review's). So a replica absorbs some 700 such attempts a second for each core that it has. A flood past that is no longer the application's to answer: it belongs to what is in front of the process, the edge (ADR-0004's Cloudflare Tunnel, or a reverse proxy's limit per address, as nginx's `limit_req`) and the operating system (the listen backlog, uvicorn's `backlog`, 2048 by default; a host firewall's limit per source address). Nothing is logged for a refusal: the routes log none, uvicorn's and websockets' lines for each handshake, and uvicorn's warning for each request that it cannot parse or upgrade, follow `[api] access_log`, off in `base.toml` since the reverse proxy logs requests already. A request that uvicorn's own code failed to parse is the exception: httptools gives that error as its own, `HttpParserCallbackError` (its parser.pyx, 0.9.0), and its warning stays, with the exception that it hides, unless that exception is httptools' own over the request, which uvicorn's callback meets as it parses the URL, such as a port past 65,535 (tried 2026-11-22): that one is a peer's error. The protocol finishes a refusal's handshake as uvicorn's pull request 3138 does, so that no error follows it.
6. **A device's reading takes `[devices.link] text_rate` characters of its text a second, in bursts of `text_burst`,** besides its messages: 256 KiB a second, in bursts of 1 MiB, the largest message. The count is the device's on the replica, shared by its connections there and kept until it is whole again, once the device holds none: one that connects again finds it as it left it, and its hello counts as any message. A frame waits, once received and before it is parsed, until the bucket holds its length, or is full; it then takes its whole length, and what the bucket lacked delays the next frame. A device that sends all it may then holds about a twentieth of a replica's event loop, and one large message is read at once. The reading only slows: the device's own sends wait behind TCP's flow control, as they do at the message rate, and nothing is dropped. AWS IoT Core delays in processing what passes its 512 KB a second; EMQX's `bytes_rate` ("1MB/s" in its example) pauses receiving a client's messages (EMQX's Rate limit, read 2026-11-21).
7. **A device's errors below the session are no error of the cloud's.** Text that is no UTF-8 fails the connection with 1007, "invalid frame payload data" (RFC 6455, 8.1 and 7.4.1), as in uvicorn, but without its error and traceback: the session ends `invalid_text`, as it ends `too_big` over a message too large, and as the cloud link has it since 3.5 (Messages, Validation). The protocol takes over uvicorn's decoding of a text message to tell it, where decoding it twice would cost about what reading its JSON costs, 0.5 to 0.8 ms for 1 MiB (2026-11-22). A frame that breaks WebSocket's rules before the handshake is answered has no close frame to answer it, where uvicorn 0.54 asserts that one was sent: the protocol closes the connection, as it would, and uvicorn writes no answer to the handshake into a connection that closes.

## Alternatives considered

| Alternative | Why not |
|---|---|
| A bucket of their own for attempts without a valid token, refusing only them, as the review proposed | It would refuse what is refused already. What it could spare is the token's check, 4 µs to 260 µs of the 1.2 to 1.8 ms that a refusal costs before the application runs, so it would not change what a flood costs; and whatever is spent before the token is anyone's to spend. |
| Pausing accepting past a rate, as EMQX's `max_conn_rate` | Paused, the listen backlog fills with the flood's connections and real devices' alike, so a host without a token delays every device. A listener's rate counts before any client authenticates; here the edge and the operating system bound what comes before the application. |
| One rate for every frame below the session, Pings, Pongs and continuations, in `config/base.toml`, as the first revision had | It closed what Sizes lets through: two messages of 1 MiB in fragments of 1 KiB, back to back, passed its burst (the second review). The cloud link 3.4 bounds the frames so that a side can limit them without refusing a message, and its values are the protocol's, not the deployment's. |
| Counting a message's frames in the Pings' allowance too, or every byte | The session paces messages by the cloud link's rates, which wait, then drop and say so; a close past them would contradict the protocol. The bytes of a message are counted by `text_rate`, its length by `ws_max_size`. |
| Capping the fragments of one message | Fragments of 1 KiB bound them already, 1024 to a message of 1 MiB, the most that `ws_max_size` lets through. |
| Checking text with an incremental decoder, fragment by fragment | uvicorn keeps a message's fragments and decodes them once whole, as does the protocol, which decodes it once; a message's length is bounded already. |
| A message's length counted on each connection, starting empty | The first message of every connection would wait. The device's own count is what the device costs, however often it connects. |
| Relying on ADR-0004's Cloudflare Tunnel for floods of frames or handshakes | A developer's own cloud runs without it, and the bounds of one device must hold there too. |
| Filtering uvicorn's error for each refusal out of the log | It would hide the same error where it is one: an application that returns without answering a handshake. |
| `TCP_USER_TIMEOUT` and TCP keep-alive on each connection, as the research of 2026-11-12 proposed with the abort | The session already ends a connection from which nothing came, or to which nothing could be sent, for two ping intervals, on every system; the abort then bounds its close. The kernel's bound would cover the same, on Linux only, and would have to stay above those two intervals so as not to cut a slow but live mobile link first. Node's ws, Go and Ranch bound a stalled write in the application too (`closeTimeout` and `terminate()`, `SetWriteDeadline`, `send_timeout_close`). |
| Replacing only uvicorn's close timer with an abort | It misses the other ways that uvicorn closes: when the application returns after a close that could not be sent, which is how a session whose device reads nothing ends, and as the server stops. |
| Waiting for uvicorn's pull requests 3230 and 3138 | 3230 is open and unmerged, 3138 merged but in no release (2026-11-22). Once uvicorn has them, decision 2 and the refusal's finish can go. |
| The legacy `websockets` protocol, the only one of uvicorn's that aborts after its close timeout | Deprecated: uvicorn says that it "will point at the websockets-sansio implementation in a future release". |
| A limit per address at the control channel | A home's devices share one address behind its router, up to `devices_per_home`, 300, and connect together after an outage, so a limit that let them through would stop no flood. A device's own limit, and the replica's, bound what the cloud spends; a reverse proxy may add one per address in front (nginx's `limit_req`). |
| One bucket for messages and their length, each message costing its length in units | Two buckets say what each bounds: messages for what handling each costs, characters for what reading costs. EMQX keeps the two apart too (`messages_rate`, `bytes_rate`). |
| Counting the time that each message takes to read, and limiting it | Exact, but known only once the message is read, and it varies with the machine: the length is known before, the same everywhere, and costs grow with it. |
| Counting UTF-8 bytes instead of characters | uvicorn hands the session a decoded text, and its reading costs by character. A character of JSON is mostly a byte. |

## Consequences

- Positive: what one device can take of a replica is bounded: the frames it sends below its messages, its connections, how often it opens them, the messages it sends, and their length, however often it connects again. A device that reads nothing no longer holds a connection, nor a stop. No host without a valid token can make a device's handshake fail, nor write the log full. A refused device is told when to try again, as the cloud link already says.
- Negative / accepted trade-offs: decisions 1, 2, 5 and 7 depend on how uvicorn 0.54 builds its sans-I/O protocol (its constructor's arguments, that it closes and writes through `self.transport`, `handle_text`, `handle_bytes`, `handle_cont`, `handle_ping`, `handle_pong`, `handle_close`, `handle_parser_exception`, `read_paused`, `pending_ping_payload`, the state of a refused handshake, and its delivery of a message, which the protocol copies for text), on httptools' `HttpParserCallbackError`, and on the lines that uvicorn and websockets log: the tests of `entry/websocket.py`, and those that flood, cut and refuse on the real server, fail if an upgrade changes them. Devices with valid tokens can still spend the replica's connections, which is what that count is for, and are told when to try again. A flood without tokens past what a replica absorbs takes its CPU until the edge or the system stops it. What a replica holds of many devices together is bounded only by how many connect: the number of connections that a replica holds is the deployment's to size.
- Follow-up: the app API's HTTP connections have no such bound for a client that reads nothing of a large answer; uvicorn's `--timeout-write` (pull request 3230) is the place for it. When uvicorn has it, decision 2 should use it instead, and when a release has pull request 3138, the protocol's finish of a refusal goes.
