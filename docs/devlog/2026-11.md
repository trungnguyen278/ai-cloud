## 2026-11-01 — Signing in, the cloud's side

**Done:** the `accounts` module, which serves ai-platform's app API 1.0, Apple aside, on [ADR-0008](../decisions/0008-data-and-tokens.md)'s libraries.
- **Signing in:** a nonce in Redis, used once and limited for each address; the ID token checked against its provider's published keys, which are kept as long as the provider's caching headers say; the token exchange.
- **Sessions:**
  - access tokens are JWTs as RFC 9068 profiles them, signed with ES256 by keys that `ai-cloud signing-key` makes;
  - refresh tokens rotate on every use, and are kept as their SHA-256; one used twice ends its session;
  - each request checks that its session still exists, so ending a session or deleting the account stops its access tokens at once.
- **The account:** reading it and changing it with an ETag; linking and removing identities; listing sessions in pages and ending them; deleting the account after a fresh sign-in.
- **Development:**
  - a provider that signs test people in, on in the development environment only;

- **Shared:** secrets from the environment or from files; the database and Redis; rate limits (GCRA, in Redis); JOSE; the protocols' schemas, read from `platform/`; Problem Details; a limit on request bodies.
- **Migrations:** one Alembic environment with a branch for each module, run by `ai-cloud migrate`, which can also write a module's next migration.
- **Review:** the locks are taken in one order (the account, its sessions, their tokens), so that no sign-in or refresh deadlocks with a deletion. Mutants of the main rules, and of the import contracts, all failed the checks.

## 2026-11-05 — Domain events, and the `worker`

**Done:** [ADR-0009](../decisions/0009-domain-events.md), and what it decides: an outbox in each module, the `worker` process that relays it to Redis Streams and hands the events to their consumers, and the accounts' first events.
- **Writing:** `accounts.outbox` (migration `accounts_0004`), which the accounts' transactions write through their `emit`, beside their change. `shared/events` declares an outbox for any module.
- **Relaying:** the worker polls every 0.5 s.
  - One relay at a time numbers each outbox's new events, under an advisory lock.
  - Each event goes to `<module>:events` with its place as its entry's identifier. So nothing is written twice, and what Redis lost, or a crash left out, is written again from the outbox.
  - Events stay 7 days in the outbox and the stream once relayed.
- **Consuming:** a consumer is a consumer group that reads from the start of the stream.
  - An event whose handler fails is tried again after 30 s, then after twice as long each time, up to 6 hours.
  - After 20 deliveries it goes to its module's dead letters, with an error in the log.
- **The accounts' events:** `accounts.member.removed.v1`, `accounts.home.deleted.v1` and `accounts.account.deleted.v1`. Deleting an account writes the events of the homes it leaves and takes along, then its own.
- **The process:** `ai-cloud worker`, with an `[events]` table in the configuration. It stops on SIGINT and SIGTERM, and on Ctrl+Break on Windows, which the tests send to a real process.
- **Tests:** against PostgreSQL and Redis, as before, which CI already starts.
- **Review:**
  - **Text:** a lone surrogate in an event's data, which a `json` column takes as an escape, would have stopped its outbox for good: Redis's client cannot encode it. An event's data now travels as ASCII JSON.
  - **Sweeps:** two workers could have swept the same rows at once. A sweep now takes the outbox's turn, as the numbering does.
  - **Tests:** the backoff test kept margins of 200 ms, thin for a busy CI machine. They are now half of each delay.
  - **Mutants:** of 44 mutants of the rules, 41 failed the tests at first. The other three showed a bug and two missing tests:
    - **A restored outbox:** the relay checked for a stream past its outbox after the round had numbered. After PostgreSQL is restored from a backup, the outbox could thus give a place again that the stream still held. Redis would refuse that event as already there, and it would be lost. The check now runs under the outbox's turn, before any place is given.
    - Nothing showed that the relay rests only when there is nothing more, nor that a consumer asks Redis for an event only once its delay has passed.

    Tests now hold all three, and the first fails on the code before the fix. The three mutants, and two more of the moved check, now fail them too.
  - The review checklist gains a section on domain events.

**Decisions:** delegated to the assistant, as the owner chose on 2026-11-03 for long-term development: all of ADR-0009.
- An outbox in each module, not one for the cloud, so that a module can still move to a database of its own.
- Polling, without LISTEN/NOTIFY, which PgBouncer's transaction pooling cannot carry, and which serializes commits.
- Places from the outbox as the stream's identifiers, rather than Redis's idempotent XADD, which remembers for a day at most.
- A growing delay between tries, so that an outage of a day or two puts nothing aside.
- No reverse-DNS prefix on the types, since the events stay in the cloud.

**Problems / unfinished:**
- **No module consumes yet.** `devices` will revoke a deleted home's devices.
- **An event about a deleted account** keeps its identifiers, and nothing else, for the retention: ADR-0006 should say so.
- **The worker's container and health check** come with the production deployment, which is not written yet.
- **Not swept yet:** idle sessions, and old first answers. They are schedules, the worker's other work.

**Next:** `devices` and set-up's registration into a home, which consumes `accounts.home.deleted.v1`. Then the worker's schedules.

## 2026-11-05 — Devices: set-up's registration into a home

**Done:** the `devices` module, the cloud's side of ai-platform's app API 1.4 ([ai-platform ADR-0012](https://github.com/trungnguyen278/ai-platform/blob/main/docs/decisions/0012-registering-devices.md)), and the first of its three steps: challenges, the registration that the app relays, a home's devices, removing one, and revoking a deleted home's devices. `platform/` moves to `app/v1.4`. [ADR-0010](../decisions/0010-device-registrations.md) says how registrations are kept.
- **Challenges:** 32 random bytes, for one home and one account, kept as their SHA-256 in `devices.challenges`: 300 s, 10 a minute for each account, for the owner and admins.
- **The registration:**
  - it is checked as set-up says: its `typ`, a public P-256 `jwk`, its ES256 signature, `aud` the configured `server`, `iss` and `sub` the same UUID, whatever their case;
  - its challenge is used first, by deleting it, in the registration's own transaction, and the answer is kept with it, a refusal included, so that a retry with its `Idempotency-Key` gets what happened;
  - one home per device, one identifier per key: the same device in its home gets `200`; any other identifier or key that the cloud holds, `409 device_taken`; a new device in a full home, `409 device_limit_reached` (300).
- **The registry:** `devices.devices`, and the keys in `devices.keys` by thumbprint, so that a device can hold two while it changes them, as the cloud link has it. A key is read one way only: strict base64url, its point on the curve and its coordinates reduced. Otherwise one key would have two thumbprints. The example's registrations, with their real signatures, verify, and give its thumbprint.
- **Reading and removing:** everyone in the home lists and reads its devices; the owner and admins remove one, which forgets its key and the first answers that show it.
- **Deletions,** in the worker: `devices.home_deletions` revokes a deleted home's devices and forgets its challenges and first answers; `devices.account_deletions` forgets what a deleted account asked for. Neither holds a lock: each deletes the challenges first, so that a registration racing it either ends first, and what it added goes too, or finds its challenge gone. Tests run both orders, for a home and for an account.
- **Shared:** the app API's conventions move from `accounts` to `shared/app_api.py`, since two modules serve the API: bodies, identifiers, pages, bearer tokens, Idempotency-Keys and problems. `[app_api] idempotency_retention` is the setting both read. `Accounts.membership` tells the other modules what an account is in a home.
- **`connected`** is false: no device connects before the cloud link's control channel. `kind`, `model` and `software` come with its `hello`.
- **Review:** of 82 mutants of the rules, 81 failed the tests at first. The other showed a missing test: a deleted home's first answers that show no device, such as a refusal's, went with it only by a statement that no test needed, since the others went with their devices. A test now holds it, and the mutant fails it.
  - **A worker that logged every event:** the revocation's log line came for a home with no devices too, which `tests/test_main.py` caught in the worker's own process. It now logs what it revoked only.
  - **A lock that did nothing:** the home's deletion first held the home, as a registration does. Its challenges, deleted first, already order the two, so it holds nothing now.
  - The review checklist gains what these met: values read from a token before it is verified, keys read one way only, deletions that cannot lock another module's rows, and handlers that log what they changed.

**Decisions:** delegated to the assistant, as the owner chose on 2026-11-03 for long-term development: all of [ADR-0010](../decisions/0010-device-registrations.md), and:
- **the steps,** each one whole: this one; then the token endpoint; then the control channel's session, with `hello`, `connected` and `bye` `revoked`. Revoking a deleted home's devices comes now rather than with the tokens, so that no device stays in a deleted home, where it would be `device_taken` elsewhere and kept past its home (PRIV-4);

## 2026-11-09 — Devices: the token endpoint

**Done:** `/device/token`, the cloud link 3.0's token endpoint, the second of the devices' three steps. A device proves who it is with an assertion that its key signs (RFC 7523, 2.2), and gets an access token.
- **The assertion:** its header names the key's thumbprint as `kid`, which `devices.keys` finds. Then come its ES256 signature with that key; `aud`, the server the device was registered with, without a trailing slash, then `/device/token`; `iat`, `exp` and `nbf` within `[tokens] leeway`; `exp` at most 5 minutes after `iat`; `iss` and `sub` naming the key's device; and `client_id`, if it comes, naming it too.
- **Once only:** each `jti` is kept in Redis, for each device, until its assertion could no longer be valid, and a second use is refused. Two requests with one assertion get one token.
- **Refusals:** `invalid_client` (401) only for a key the cloud does not hold: never registered, removed, or gone with its home. The device then offers set-up. Any other failure is `invalid_request`, after which the device tries again later. Over `[devices.token_rate]`, 60 a minute for each address, the answer is 429 with `Retry-After`.
- **The access token:** the cloud's own JWT, as the app's (RFC 9068): `at+jwt`, its audience `device`, so that neither an app's nor a device's passes for the other. `sub` and `client_id` name the device; `[devices] access_lifetime` is 600 s.
- **Shared:** OAuth's form and errors move from the accounts' routes to `shared/oauth.py`, which both token endpoints use. A device identifier is read in one place for registrations and assertions.
- **Review:** PyJWT reads a NumericDate with `int()`, so `"iat": "1700000000"` or `true` passed its checks, and arithmetic on them would have failed as a 500. The assertion's times are now checked as JSON numbers. A request with an assertion and another credential, a `client_secret` or an `Authorization` header, is refused (RFC 6749, 2.3). Refusals are logged with their reason, never the assertion, but not those over the rate, which a flood would multiply.
- **Mutants:** all 40 mutants of the new rules fail the tests. Three needed a test of their own first: an assertion of five minutes exactly, a server with a trailing slash, and an unknown key while another device is registered.

**Decisions:** delegated to the assistant, as the owner chose on 2026-11-03:
- **`invalid_client` for unknown keys only.** RFC 7523, 3.2, gives it to every client JWT that fails, but the cloud link has the device offer set-up after it: a clock far off would then unbind a device. The cloud link lets any other code stand for "try again later", and `invalid_request` says that the request, not the device, was wrong.
- **The used `jti` in Redis,** as the sign-in's nonces are (ADR-0008, decision 3): losing them reopens, for 5 minutes at most, the replay of an assertion copied in that time, which TLS already keeps from others.
- **A limit for each address,** before any work: it bounds what anyone can make the cloud do, and lets a home's devices, behind one address, get their tokens together after an outage.
- **The registry alone decides:** a device whose key the cloud holds gets a token. A deleted home's keys go with the worker's consumer, within a second normally. A token issued just as its device is removed is refused when it opens the control channel, which checks the registry too.

**Problems / unfinished:**
- **Nothing reads the tokens yet:** the control channel, the next step, checks them, and the registry, at its handshake.
- **For ai-platform:** the cloud link could name the code for an assertion that fails while its key is known, which RFC 7523 would make `invalid_client`, and say that the endpoint may answer 429.

**Next:** the control channel's session: `hello`, `connected`, and `bye` `revoked`.

## 2026-11-11 — Devices: the control channel's session

**Done:** the cloud link 3.0's control channel, `/device/v3/link`, the third of the devices' steps: a device connects, says what it is, and is told when it is replaced or revoked. [ADR-0011](../decisions/0011-control-channels.md) says how the replicas share it.
- **The handshake:** the device's access token, then the registry. A device removed, gone with its home, or registered again since its token, gets 401 as Problem Details, and a replica going away 503.
- **The hellos:** the device's comes first, and the registry keeps its kind, model and software, which the app API's devices now show. The cloud answers with a new session, its time and `ping_interval`, without conversations or events yet. Another major gets `bye` `unsupported_protocol`; a first message that is no hello, or none in `hello_timeout`, `bye` `no_hello`. A conversation the device names, which the cloud does not hold, ends `lost`.
- **The session:** pings get pongs with the last number taken; numbers are checked (a duplicate is ignored, a skip ends the session `out_of_sequence`); a message that fails the schema gets `invalid_message`; a conversation request gets `unavailable`; what the cloud does not take yet is ignored. The cloud reads `rate` messages a second from a device, pings included, `burst` at once, with `backlog` waiting their turn, and tells it once when it drops some. A connection silent for two ping intervals closes, and so does one to which nothing could be sent for as long; a message over 1 MiB closes it too.
- **Presence and hints:** `connected` reads the presence in Redis, which names each device's newest connection. A newer connection, a removal and a home's deletion send a hint, which every replica hears; each also checks its connections every `check_interval`, against the registry and the presence, so that a lost hint delays a `bye` and never loses one.
- **Going away:** before uvicorn closes the WebSockets, the api sends `reconnect` on each session.
- **The example** `devices.json` runs whole, with a robot of the tests' own that connects and is told it is removed where the example says, against uvicorn on a port of the machine.
- **Shared:** a request's bearer token is read in `shared/oauth.py` for the app and the devices. The tests' devices connect with `websockets`, which uvicorn already brought, now in the tests' dependencies.
- **Review:**
  - **Pings came before any rate:** a device could have the cloud parse and answer pings without bound. The rate now counts every message, before it is read.
  - **What a device does not read waited without bound,** and so did the last close, which uvicorn holds while the device's window is full. A device that takes nothing for two ping intervals now seems gone, as a silent one does, and the last close waits `close_timeout` at most. Bounding what waits by a count did not do: one burst of answers, which the handler makes without yielding, passed the backlog.
  - **A replica's check of its devices** passed them to `IN`, a parameter each, and asyncpg takes 32,767 at most: it passes one array now.
  - **The server's shutdown** stopped short when asking the devices to connect again failed: it logs the failure, and stops.
  - **Mutants:** of 72 mutants of the new rules, 70 failed the tests at first. The other two showed that the test's numbers that are booleans or duplicates came after numbers that made them duplicates anyway: in another order, both mutants fail it. The 18 mutants of what the review changed, and of the sessions' rules again, all fail the tests.
- **Second review:**
  - **What a device sent could crash its own session.** A `type` that is a list or an object raised `TypeError` where the cloud looked it up, and JSON nested some ten thousand deep raised `RecursionError` (11,331 on Windows). The schema's `uniqueItems`, as jsonschema checks it, compared 4,000 small objects in 17 s, which blocked every session of the replica, and recursed as deep as they nested. One reader, `read_json`, now serves the link and the app API's bodies alike. It refuses what is not JSON, and what the protocols' values cannot hold: NaN, numbers past a double such as `1e400`, which Python reads as an infinity, lone surrogates, and nesting deeper than `max_json_depth`. In a session, what the cloud cannot read is ignored, as before. A type that is no text is numbered, and fails the schema with `invalid_message`. `uniqueItems` is checked only on an array that its schema's `maxItems` and `items` allow, and a test keeps every such array bounded. Anything else that fails in the cloud's own code ends the session with `bye` `error` and close 1011, and is logged.
  - **A server's stop waited for ever** on a connection whose device reads nothing, for uvicorn waits for every connection to close. `[api] shutdown_timeout`, uvicorn's `timeout_graceful_shutdown`, bounds that wait at 3 s, then uvicorn cancels what is left. A session cut so still forgets its presence: the replica waits up to `close_timeout` for its sessions to leave before Redis closes. The presence lapses in `presence_ttl` otherwise, and the registry's row holds nothing of a session.
  - **What a session logs once** was kept for each type a device named, without bound. Its keys are fixed now, and only the first type the cloud does not take is named.
  - **A handshake whose registry read overlapped `going_away`** opened a session after the others had been asked to connect again. The handshake checks again after the read, and answers 503. A session that begins then anyway closes with 1012 before its hello, as those held then do.
  - **Mutants:** of 31 mutants of the fixes, 30 failed the tests at first. The other one showed that the test of `uniqueItems` only gave it items that its `items` refused, so that `maxItems` was never needed: objects that the array may hold are now among them.

**Decisions:** delegated to the assistant, as the owner chose on 2026-11-03: all of [ADR-0011](../decisions/0011-control-channels.md), and:
- **the steps:** this one; then resuming sessions, with their state in Redis so that another replica takes them; then `update_required`, and 410 for a retired major, with `updates`;
- **a deleted home's devices:** the second review of the token endpoint found that they keep getting tokens until the worker's consumer runs, and so connect. The channel does not ask the accounts at its handshake: the registry alone decides, as at the token endpoint, so that the two never disagree; such a check would only cover connections opened within the lag, while devices stay connected; and every module's data of a deleted home lags as long (ADR-0011, decision 9);
- **two reasons the cloud link leaves open:** a first message that is no hello the cloud can read ends the session with `no_hello`, as the robot ends one whose cloud's hello it cannot read; a ping the cloud cannot read, with `error`, the reason a side takes for one it does not know. A device acts the same on either;
- **what the cloud cannot read** (second review): numbers past a double are left out, as I-JSON leaves them out (RFC 7493, 2.2), and so is nesting deeper than `max_json_depth`, as RFC 8259 lets a reader limit it (section 9). In a session, such a frame is ignored, for it has no number to answer. A failure of the cloud's own ends the session with `bye` `error` and 1011, RFC 6455's unexpected condition;
- **the shutdown's bound,** 3 s after `close_timeout`, so that a stop fits within the 10 s that Docker Compose waits by default (`stop_grace_period`, docs.docker.com, read 2026-11-12). uvicorn calls it `--timeout-graceful-shutdown` (uvicorn.dev/settings).
- **the depth of JSON** (CI of the second review): Python's reader fails 11,331 levels deep on Windows and reads 20,000 on Linux, where the C stack sets it, so a test that expected a refusal failed on CI. The depth is a setting now, `[app_api] max_json_depth` for the app API's bodies and `[devices.link] max_json_depth` for a device's messages, 64 in both (.NET's `JsonReaderOptions.MaxDepth` default, learn.microsoft.com, read 2026-05-27; the bodies and messages nest a few levels). `read_json` walks the parsed value level by level, without recursion; `RecursionError` stays caught for what Python's reader cannot follow.

**Problems / unfinished:**
- **For ai-platform:** the cloud link could name the `bye` reason for a hello or a ping that a side cannot handle ("Errors").
- **For ai-platform:** the cloud link could name the depth of nesting that a side reads.
- **Left for a later change** (second review): a connection whose device never reads stays open until the server stops, and the handshake has no limit of its own; a NUL in `software`, and in the app API's bodies.
- **Until resuming comes,** each connection's loss ends its session, and a message over 1 MiB closes its connection without its `invalid_message`.
- **Not checked:** a real robot on the channel, a proxy such as Cloudflare in between, and many devices at once.

## 2026-11-18 — JSON every side holds: the cloud link 3.1 and the app API 1.6

**Done:** the cloud's part of [ai-platform ADR-0014](https://github.com/trungnguyen278/ai-platform/blob/main/docs/decisions/0014-json-every-side-can-hold.md), as the cloud link 3.1 and the app API 1.6 say it. `platform/` is pinned at `app/v1.6`.
- **What the cloud reads** (`shared/protocols.py`, `read_json`): it refuses, as `Unreadable`, with a message of its own that names no value:
  - a U+0000 or a lone surrogate, in a name or a string, at any depth;
  - nesting deeper than 64, counting the outermost level, as the protocols fix it (ADR-0014, decision 3). It is counted on the text, outside its strings, before the text is parsed, so that Python's reader, whose limit the C stack sets, never meets deeper;
  - a name repeated in an object, which I-JSON forbids (RFC 7493, 2.3);
  - a number past a double's range, however it is written: `1e400`, or the same number as an integer, which Python holds and JavaScript's `JSON.parse` takes for an infinity;
  - bytes that are not UTF-8, the only encoding of I-JSON (RFC 7493, 2.1). A byte order mark is no JSON.
- **The app API 1.6:** a body the cloud does not read gets `400`, whose detail says why. A U+0000 in a body failed in PostgreSQL before, as a `500`.
- **The control channel, 3.1:**
  - **A frame that the cloud cannot answer** ends the session with `bye` `invalid_message`, before the hello as after it: a binary frame; no JSON that every side holds; no object; no type that is text; a numbered type without its number; a `hello`, `ping`, `pong` or `reconnect` that fails the schema. The bye's `message` says why, for the device's logs; the cloud logs only the reason. Before, such frames were ignored, or ended the session `no_hello` before the hello, and a failing ping ended it `error`.
  - **A numbered message that fails** still gets `error` `invalid_message`, and the session goes on.
  - **A connection closed with 1009,** by uvicorn past `ws_max_size` or by the device, ends its session, which the log names `too_big`.
  - **A `seq` of `1.0`** is the number 1, as JSON Schema's integers are.
  - **The cloud answers 3.1** to a hello of 3.1 or later.
- **The token endpoint, 3.1:** `invalid_request` for an assertion that is no JWT or names no key; `invalid_grant` for one of a key the cloud holds that fails: its signature, times, audience or issuer, a `jti` seen before, or a `client_id` that names another device; `invalid_client` (`401`) only for a key the cloud does not hold. `429` is as before.
- **ADR-0011** is marked amended by the cloud link 3.1.
- **Review:**
  - **uvicorn refuses a message sent after a close that it sent itself,** as past `ws_max_size`, with a `RuntimeError`, until it sees the connection lost (uvicorn 0.54.0, `websockets_sansio_impl.py`, `send`). A pong sent in that window would have failed the session, with a traceback in the log. The adapter takes it as a closed connection, and checks the client's state before it sends or closes; a test of the adapter, against Starlette's WebSocket, refuses as uvicorn does.
  - **Integers past a double's range were held,** while the same number written `1e400` was refused, and one of more than 4,300 digits was "not JSON". All three are now past a double's range.
  - **Repeated names hid what the cloud must refuse** (the coordinator's review, 2026-11-19). Python's reader keeps the last value of a name and drops the others unread, so `{"x": "\u0000", "x": "ok"}` passed, and so did a dropped value nested 100 deep. One nested 15,000 deep was refused on Windows and read on Linux. A hello whose `device` came twice, the first holding U+0000, opened its session. The cloud now refuses repeated names, and counts the depth on the text first.
  - **The depth was a setting** that a deployment could set below the protocols' 64, and its comments said that the protocols name no depth. It is the protocols' value now, in the code.
  - **A pattern for a JSON string that required its closing quote** was quadratic: over 20,000 escaped quotes it took 6.4 s, for each could start a string. Without its closing quote, a string runs to the end of the text, and the same text takes milliseconds; a test times it.
  - **Mutants:** 40 run, on the reader, the session, the bye, the adapter, the token endpoint and the app's bodies, all killed; then 16 on the review's fix, 15 killed, and the survivor (an object's values unchecked) killed by a test of U+0000 in a value.
- **The checklist** gains five bug classes: U+0000 and lone surrogates in JSON read any other way than `read_json`; a check of the value a parser returns, which misses what it dropped; a frame that cannot be answered, ignored; a server's own close, which the adapter must expect; and a pattern that can fail after a long match.

**Decisions:** delegated to the assistant, as the owner chose on 2026-11-03:
- **What the cloud holds of what I-JSON forbids:** noncharacters, and numbers more precise than a double, which ADR-0014 lets a receiver take (decision 4). It refuses numbers past a double's range, in either spelling, so that the answer depends on the number.
- **Repeated names are refused,** which decision 4 allows, rather than kept with each dropped value checked. No sender repeats a name (decision 1), so refusing costs no message; I-JSON forbids them (RFC 7493, 2.3); and a value that one parser drops and another keeps is a second message in the same text. Go's `encoding/json/v2` refuses them too: it "reports an error if a JSON object contains a duplicate name" (go.dev/blog/jsonv2-exp, 2025-09-09). Python's `json` keeps the last silently, and points to `object_pairs_hook` for another way (docs.python.org/3.14/library/json.html, read 2026-11-19).
- **The depth is not a setting:** `shared/protocols.py`'s `MAX_DEPTH`, 64. ADR-0014 fixes what every side reads at least, and that no side sends deeper, so that "a device knows how deep the cloud reads": lower would break the protocols, and deeper would serve no message, and would let Python's reader meet the C stack's limit again. AGENTS.md keeps a value that a protocol fixes in the code that speaks it, once.
- **A first message that the cloud can answer, but no hello,** ends the session `no_hello` at once, as in 3.0. The protocol names `no_hello` for a hello that did not come in time, and says nothing of another message that comes first. A `ping`, `pong` or `reconnect` that fails gets `invalid_message`, as the protocol says such a frame does, whenever it comes.
- **A valid `hello`, `pong` or `reconnect` in a session** is ignored, and logged once: the hello came already, and the others are the cloud's to send.
- **The bye's `message`** is the cloud's own words, and the schema's for a message that fails, which name where and which rule, never a value. It is cut to 256 characters, `short_text`.
- **A close with 1009 ends the session as `too_big`,** whichever side closed, so that resuming, the next step, does not take it up again: the cloud link's Sizes says that both sides end the session.
- **The token endpoint's split** follows the table of the cloud link 3.1 and RFC 6749 (5.2): a grant "issued to another client" is `invalid_grant`, so a `client_id` that names another device is too.

**Problems / unfinished:**
- **For ai-platform:** the cloud link does not say what a first message that is not a hello gets, when the cloud can answer it. The cloud keeps `no_hello`.
- **For what one device can exhaust** (the next task after 3.2): counting the depth costs up to some 65 ms for a MiB of brackets, the worst text, where `json.loads` takes some 30 ms (Windows, 2026-11-19); reading a MiB took 110 to 240 ms before it.
- **Next:** the cloud link 3.2's `leave`, then resuming a session.

## 2026-11-19 — Devices: leaving the home (the cloud link 3.2)

**Done:** the cloud's part of [ai-platform ADR-0015](https://github.com/trungnguyen278/ai-platform/blob/main/docs/decisions/0015-factory-reset.md), as the cloud link 3.2's `leave` says it. `platform/` is pinned at `cloud/v3.2`.
- **`leave`,** in a session of 3.2: the cloud removes the device as the app's `DELETE` does, with the same store calls under the same locks (the home, then its first answers, then the device): the app no longer lists it, the cloud forgets its key, its tokens and its assertions are refused (`401`, `invalid_client`), and a hint ends its other connections. Then the session ends with `bye` `left`, and closes with 1000.
- **A removal that fails** gets `error` `internal`, "the device could not be removed", as the protocol's example has it, and the session goes on: the device may ask again.
- **A removal in the app, or the home's deletion, that came first:** the session ends with `bye` `revoked`, which the protocol says means the same to the device. The leave removes only the registration that its session opened under: a device removed and registered again since keeps its new one.
- **A `leave` in a session of 3.1** is a type the cloud does not take, logged once and ignored, as a cloud of 3.1 would.
- **The cloud answers 3.2** to a hello of 3.2 or later.
- **Conversations:** the cloud holds none yet, so a device's leave has none to end. The conversations module will end them where the removal does.
- **ADR-0011** is marked amended by the cloud link 3.2.
- **Races, settled in the design:**
  - **The removal's own hint would end the session `revoked`:** it reaches this replica too, whose check would find the device gone before the leave says `left`, and so could the check that runs every `check_interval`. A session whose leave is under way is left to that leave; one whose leave failed is checked again. A test hears the hint before the leave ends.
  - **Holding the device's row first,** as a rename does, would take it before its first answers, which a home's deletion takes in the other order: the two would wait for each other. The leave reads the device under the home's lock, as the app's removal takes it, and the removal's answer says whether the home's deletion, which does not hold the home, came first.
  - **A second `leave`, queued behind the first,** would start a removal of its own once the session had ended. What waits once a session ends is no longer handled.
- **Review:** the leave's lock order had no test: a removal that held the device's row first, as a rename does, passed every test. A test now holds the device's first answer, as a home's deletion does, and takes the device while the leave waits.
- **Mutants:** 18 run, on the session, the removal, the version and the lock order, all killed.
- **The checklist** gains one bug class: a session that ends itself after a change, ended first by the check that its own change brings.

**Decisions:** delegated to the assistant, as the owner chose on 2026-11-03:
- **The device's session is its authority** to remove itself: no person's role is checked, for "only its own session can send" `leave` (SEC-6). The log says that a device left its home, apart from a person's removal.
- **The leave removes the registration its session opened under,** or none: the session knows the device's home and registration from its handshake, which `Opening` now carries. A registration is in one home, since registering a device that another home holds is refused, `device_taken`.
- **A device removed meanwhile gets `revoked`, not `left`:** `left` says that the device left "as its `leave` asked", and the protocol names `revoked` "from a removal in the app meanwhile" as the same outcome for the device.
- **A removal cut short by the session's end** (the connection lost, or the replica going away) commits or rolls back, as any transaction: either the device is out, and its next token is refused with `invalid_client`, which it takes for the outcome, or it sends a new `leave` in its next session (leave, An answer lost with the connection). A hint lost with it is found by the next check.
- **`Session.left` is now `finished`,** and the presence's `_leave` is `_forget`, so that "leave" and "left" name the protocol's message and bye only.

**Problems / unfinished:**
- **For ai-platform:** the app API's README says that the cloud does not yet implement 1.6; it does since ai-cloud#29.
- **Next:** what one device can exhaust, then resuming a session.

## 2026-11-21 — What one device can exhaust (SEC-15)

**Done:** [ADR-0012](../decisions/0012-what-one-device-can-exhaust.md), proposed, bounds what one device can take of a replica besides its messages, each with a setting in `config/base.toml`:
- **A connection that the server closes ends within `[api] ws_close_timeout`** (2 s), read or not. `entry/websocket.py` runs uvicorn's sans-I/O protocol on a transport whose `close` aborts it once the timeout has passed, and whose closing handshake waits as long for the device's close frame, where uvicorn waits 10 s. A device that read nothing kept its connection for ever once its session ended, since every way that uvicorn 0.54 closes is asyncio's `close`, which waits for the buffer to leave; a stop waited for it until `shutdown_timeout`.
- **A device opens its control channel `[devices.connection_rate]` times a period** (10, then one every 6 s), counted in Redis for the device that its token names, once the token verifies and before the registry is read. Past it, 429 with `Retry-After`.
- **A replica takes `[devices.link] connect_rate` handshakes a second** from all devices (100, in bursts of 200), counted before any token's signature. Past it, 503 with `Retry-After`. uvicorn's `limit_concurrency` does not count upgrades.
- **A session reads `[devices.link] text_rate` characters a second** (256 KiB, in bursts of `text_burst`, 1 MiB), besides its messages. Reading 1 MiB costs from 11 ms (one long string) to 190 ms (small numbers) here, and the schema under 2 ms, so one device at its message rate could hold most of a replica's event loop.
- **A rate's message says its wait in whole seconds, rounded up,** as `Retry-After` does: 0.2 s read "retry after 0 s", in the devices' and the accounts' errors.
- **Already fixed, now confirmed:** a U+0000 in a hello's `software` or in an app request's JSON is refused by `read_json` since #29, before PostgreSQL (tests in `test_link.py`, `test_sessions.py`, `test_devices.py`, `test_account.py`); a message's `type` is checked by the schema, 64 characters at most, before the session would log it.
- **Review:** a handshake without a token was refused, and logged, before any count, so a flood of them had no bound: the replica's count now comes first. `Retry-After` was rounded in three places, and the control channel's 429 in none that a test checked exactly: one function rounds it now, and the 429's detail must say the same seconds as its header. The 429's test used one token throughout, so a count by token would have passed: its third attempt has a new one. The per-device test would have hung, not failed, on a count after the registry: it is bounded. The full suite found `test_main.py` without the new setting.
- **Mutants:** 24 run, on the cut, the counts, the buckets, the rounding and the wiring. 21 of the first 23 were killed: the device's count moved past the registry hung its test instead of failing it, and `Retry-After` rounded down survived; both are killed now, with a 24th on handshakes without a token.
- **The checklist** gains four: a close bounded by the side that closes, a limit before the step it spares and on what the client cannot change, a bucket whose cost can exceed its burst, and a test that holds a step open without a bound.

**Decisions,** delegated to the assistant (the ADR weighs the alternatives):
- **The cut in the application, not `TCP_USER_TIMEOUT`,** which the research of 2026-11-12 proposed with it: the session already ends a connection that is silent or stalled for two ping intervals, on every system; the kernel's bound would be Linux's only, and would have to stay above them. Node's ws (`closeTimeout`, `terminate()`), Go (`SetWriteDeadline`) and Ranch (`send_timeout_close`) bound it in the application too.
- **Wrapping the transport,** not only uvicorn's close timer: the session of a device that reads nothing ends when the application returns, and the stop closes every connection, and neither goes through the timer. uvicorn's pull request 3230, `--timeout-write`, was still open on 2026-11-21 (last updated 2026-10-25; 0.54.0 of 2026-09-25 is the latest release).
- **A limit per device after the token, not per address:** a home's devices share its router's address, up to 300 of them, and connect together after an outage. AWS IoT Core takes one CONNECT a second from each client ID (its quotas, read 2026-11-21); a device's backoff, a new token and a replica going away make a few in a row, so the limit allows ten at once.
- **The replica's count in its own memory:** what a flood costs before its tokens are checked is this replica's CPU, and a shared count would put a round trip to Redis before each refusal. It counts every attempt, with a token or without: one without was refused, and logged, before any count.
- **Characters, not bytes:** uvicorn hands the session a decoded text, whose reading costs by character. AWS IoT Core delays what passes 512 KB a second on a connection, and EMQX's `bytes_rate` pauses a client's reading (both read 2026-11-21).
- **A cost past the burst is owed:** the devices' settings cannot read the domain's 1 MiB, so a message longer than `text_burst` waits for a full bucket, and what it lacked delays the next.
- **Nothing more on the wire:** the cloud link's Refusals already say what 429 and 503 mean, and that a device waits for `Retry-After`.

**Problems / unfinished:**
- **The app API's HTTP connections** have no bound for a client that reads nothing of a large answer: uvicorn's `--timeout-write` (pull request 3230) is the place, and decision 1 should then use it too.
- **How many connections a replica holds** is the deployment's to size: the limits bound each device and the rate of new ones, not their number.
- **Next:** resuming a session.

## 2026-11-22 — What one device can exhaust: the review of ai-cloud#32 (SEC-15)

**Done:** the review of #32 found six problems, each confirmed against the real server, and [ADR-0012](../decisions/0012-what-one-device-can-exhaust.md), still proposed, is revised for them:
- **Frames below the session are bounded.** uvicorn 0.54 handles each Ping, Pong and continuation frame as it parses it, so no rate of the session saw them: empty Pongs held a replica at 100% CPU and raised an honest device's ping to pong from 2.5 to 280 ms; Pings from a device that read nothing grew the write buffer to 156 MB in 12 s, since uvicorn writes each Pong whatever the transport takes; empty continuation frames piled up 1.7 million in uvicorn's list in 6 s. `entry/websocket.py` now counts them against `[api] ws_frame_rate` (256 a second, in bursts of `ws_frame_burst`, 1024) and closes with 1008 past it, parses a burst's worth at a time and no further than the application has taken, and lets only the latest Pong wait for the transport. Against the reviewer's probes the flooder is cut at once, the honest device's ping keeps its 2 ms (3 to 5 ms at most), the buffer stays empty, and the session ends `flooded`.
- **No attempt without a valid token spends a limit.** The replica's count came before the token's signature, so one host without a token, at 619 attempts a second, refused real devices 503. `Links.open` now checks the signature first, without I/O, then the device's count, then the replica's, which only verified handshakes spend.
- **Reading is the device's, the hello included.** Each connection's buckets started whole, and the hello was read outside them: a burst of 10 connections had the replica read 20 MiB at once. A `Budget` per device on the replica, which its sessions share and which is swept once whole with no session, takes the hello's length too.
- **Redis down at the device's count is a 503** with Problem Details (`RatesUnavailable`), not uvicorn's plain-text 500 and a traceback for each attempt; any other failure there is logged and answered 500 with Problem Details.
- **A refusal writes nothing.** The routes log none; uvicorn's line for each handshake, websockets' beside it, and uvicorn's warning for each request that it cannot parse or upgrade follow `[api] access_log`; and the protocol finishes a refused handshake, whose unfinished state had uvicorn log an error for each ("ASGI callable returned without completing handshake", found while testing; uvicorn's pull request 3138 fixes it, merged 2026-10-25 and in no release on 2026-11-22). 1,600 refused attempts wrote no line.
- **The close bound the ADR states is what the code does:** one `close_timeout` covers the session's bye and its close, so a device that reads nothing is cut at most `close_timeout` and twice `ws_close_timeout` after its session ends, 9 s, where it was 14 s.
- **What a refusal costs**, measured (400 in a row of each, twice; Windows 11, CPython 3.14, asyncio): 1.2 to 1.4 ms of a core without a token or with one that is no JWT, 1.6 to 1.8 ms with a forged signature, 2.1 to 2.5 ms past a device's rate. About 700 a second for each core: past that, a flood is the edge's and the system's, which the ADR now says.
- **Review:** two Pings in one read left an empty answer waiting in place of the latest Pong, and a close's answer read with a Ping waited with its Pong and was lost: websockets answers all the frames of a read in one `data_to_send`. Only an answer that holds something replaces the waiting one now, and a close sends it first; both tests failed before. uvicorn's warning for each request it cannot parse or upgrade wrote a line for each too, and follows `access_log` now. The route's 500 and the one deadline of a session's end had no test; the unit test of a refusal saw no log at all, since uvicorn's default logging keeps `uvicorn.error` from the root: it now listens to that logger, and the protocol's tests leave the process's logging alone.
- **Mutants:** 33 run, on the frame bucket, the Pong that waits, the parsing, the refusal, the filter, the order of the counts, the budgets, the deadlines and the 503. 30 were killed at first: the refusal's (its unit test saw no log) and the sweep's (no test ran it from the check loop) are killed now by the tests above, and `read_on`'s test of what is left unparsed was removed, since what is left only waits while reading is paused.
- **The checklist** replaces the limit before the step it spares with a limit after the token's check, and gains four: length counted per device with the hello, frames below the application, a dependency failing inside a handshake, and nothing anyone sends writing a line for each attempt, a test of uvicorn's log lines that can see them, and what websockets answers by itself for a whole read; a stated bound adds up every wait before it.

**Decisions,** delegated to the assistant (the ADR weighs the alternatives):
- **Closing, not pacing, past the frame rate,** as Envoy closes an HTTP/2 connection flooded with control or empty frames (CVE-2019-9512 and 9518): a device has no reason to send 256 of them a second, and pausing would leave the parsed frames in memory. Messages' own frames are not counted: the session paces them, as the cloud link says.
- **No fragment cap of its own:** the frame rate and `ws_max_size` bound a fragmented message already.
- **No bucket for attempts without a valid token,** as the review proposed: its check would spare 4 to 260 µs of the 1.2 to 1.8 ms that a refusal costs before the application runs, and would be one more count that anyone spends. Nor pausing accept past a rate, as EMQX does: the backlog would then fill with the flood's connections and the devices' alike.
- **The refusal finished in the protocol, not its error filtered:** a filter would hide the same error where it is a bug, an application that answers no handshake.
- **Unparsable requests' warnings follow `access_log`,** as nginx logs "client sent invalid request" at its info level, below its default (read 2026-11-22).

**Problems / unfinished:**
- **The token endpoint logs each refusal,** within `[devices.token_rate]` for each address; and the app API's HTTP endpoints answer a Redis failure with the generic 500.
- **Measured on Windows only:** the reviewer measured the frame floods on Linux too, with uvloop and asyncio, but not the fix.
- **uvicorn's pull request 3138,** once released, makes the protocol's `send` override needless: its test then still passes without it.
