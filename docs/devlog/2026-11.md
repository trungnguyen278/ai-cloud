## 2026-11-01 — Signing in, the cloud's side

**Done:** the `accounts` module, which serves ai-platform's app API 1.0, Apple aside, on [ADR-0008](../decisions/0008-data-and-tokens.md)'s libraries.
- **Signing in:** a nonce in Redis, used once and limited for each address; the ID token checked against its provider's published keys, which are kept as long as the provider's caching headers say; the token exchange.
- **Sessions:**
  - access tokens are JWTs as RFC 9068 profiles them, signed with ES256 by keys that `ai-cloud signing-key` makes;
  - refresh tokens rotate on every use, and are kept as their SHA-256; one used twice ends its session;
  - each request checks that its session still exists, so ending a session or deleting the account stops its access tokens at once.
- **The account:** reading it and changing it with an ETag; linking and removing identities; listing sessions in pages and ending them; deleting the account after a fresh sign-in.
- **Development:**
  - a provider that signs test people in, on in the development environment only;

- **Shared:** secrets from the environment or from files; the database and Redis; rate limits (GCRA, in Redis); JOSE; the protocols' schemas, read from `platform/`; Problem Details; a limit on request bodies.
- **Migrations:** one Alembic environment with a branch for each module, run by `ai-cloud migrate`, which can also write a module's next migration.
- **Review:** the locks are taken in one order (the account, its sessions, their tokens), so that no sign-in or refresh deadlocks with a deletion. Mutants of the main rules, and of the import contracts, all failed the checks.

## 2026-11-05 — Domain events, and the `worker`

**Done:** [ADR-0009](../decisions/0009-domain-events.md), and what it decides: an outbox in each module, the `worker` process that relays it to Redis Streams and hands the events to their consumers, and the accounts' first events.
- **Writing:** `accounts.outbox` (migration `accounts_0004`), which the accounts' transactions write through their `emit`, beside their change. `shared/events` declares an outbox for any module.
- **Relaying:** the worker polls every 0.5 s.
  - One relay at a time numbers each outbox's new events, under an advisory lock.
  - Each event goes to `<module>:events` with its place as its entry's identifier. So nothing is written twice, and what Redis lost, or a crash left out, is written again from the outbox.
  - Events stay 7 days in the outbox and the stream once relayed.
- **Consuming:** a consumer is a consumer group that reads from the start of the stream.
  - An event whose handler fails is tried again after 30 s, then after twice as long each time, up to 6 hours.
  - After 20 deliveries it goes to its module's dead letters, with an error in the log.
- **The accounts' events:** `accounts.member.removed.v1`, `accounts.home.deleted.v1` and `accounts.account.deleted.v1`. Deleting an account writes the events of the homes it leaves and takes along, then its own.
- **The process:** `ai-cloud worker`, with an `[events]` table in the configuration. It stops on SIGINT and SIGTERM, and on Ctrl+Break on Windows, which the tests send to a real process.
- **Tests:** against PostgreSQL and Redis, as before, which CI already starts.
- **Review:**
  - **Text:** a lone surrogate in an event's data, which a `json` column takes as an escape, would have stopped its outbox for good: Redis's client cannot encode it. An event's data now travels as ASCII JSON.
  - **Sweeps:** two workers could have swept the same rows at once. A sweep now takes the outbox's turn, as the numbering does.
  - **Tests:** the backoff test kept margins of 200 ms, thin for a busy CI machine. They are now half of each delay.
  - **Mutants:** of 44 mutants of the rules, 41 failed the tests at first. The other three showed a bug and two missing tests:
    - **A restored outbox:** the relay checked for a stream past its outbox after the round had numbered. After PostgreSQL is restored from a backup, the outbox could thus give a place again that the stream still held. Redis would refuse that event as already there, and it would be lost. The check now runs under the outbox's turn, before any place is given.
    - Nothing showed that the relay rests only when there is nothing more, nor that a consumer asks Redis for an event only once its delay has passed.

    Tests now hold all three, and the first fails on the code before the fix. The three mutants, and two more of the moved check, now fail them too.
  - The review checklist gains a section on domain events.

**Decisions:** delegated to the assistant, as the owner chose on 2026-11-03 for long-term development: all of ADR-0009.
- An outbox in each module, not one for the cloud, so that a module can still move to a database of its own.
- Polling, without LISTEN/NOTIFY, which PgBouncer's transaction pooling cannot carry, and which serializes commits.
- Places from the outbox as the stream's identifiers, rather than Redis's idempotent XADD, which remembers for a day at most.
- A growing delay between tries, so that an outage of a day or two puts nothing aside.
- No reverse-DNS prefix on the types, since the events stay in the cloud.

**Problems / unfinished:**
- **No module consumes yet.** `devices` will revoke a deleted home's devices.
- **An event about a deleted account** keeps its identifiers, and nothing else, for the retention: ADR-0006 should say so.
- **The worker's container and health check** come with the production deployment, which is not written yet.
- **Not swept yet:** idle sessions, and old first answers. They are schedules, the worker's other work.

**Next:** `devices` and set-up's registration into a home, which consumes `accounts.home.deleted.v1`. Then the worker's schedules.

## 2026-11-05 — Devices: set-up's registration into a home

**Done:** the `devices` module, the cloud's side of ai-platform's app API 1.4 ([ai-platform ADR-0012](https://github.com/trungnguyen278/ai-platform/blob/main/docs/decisions/0012-registering-devices.md)), and the first of its three steps: challenges, the registration that the app relays, a home's devices, removing one, and revoking a deleted home's devices. `platform/` moves to `app/v1.4`. [ADR-0010](../decisions/0010-device-registrations.md) says how registrations are kept.
- **Challenges:** 32 random bytes, for one home and one account, kept as their SHA-256 in `devices.challenges`: 300 s, 10 a minute for each account, for the owner and admins.
- **The registration:**
  - it is checked as set-up says: its `typ`, a public P-256 `jwk`, its ES256 signature, `aud` the configured `server`, `iss` and `sub` the same UUID, whatever their case;
  - its challenge is used first, by deleting it, in the registration's own transaction, and the answer is kept with it, a refusal included, so that a retry with its `Idempotency-Key` gets what happened;
  - one home per device, one identifier per key: the same device in its home gets `200`; any other identifier or key that the cloud holds, `409 device_taken`; a new device in a full home, `409 device_limit_reached` (300).
- **The registry:** `devices.devices`, and the keys in `devices.keys` by thumbprint, so that a device can hold two while it changes them, as the cloud link has it. A key is read one way only: strict base64url, its point on the curve and its coordinates reduced. Otherwise one key would have two thumbprints. The example's registrations, with their real signatures, verify, and give its thumbprint.
- **Reading and removing:** everyone in the home lists and reads its devices; the owner and admins remove one, which forgets its key and the first answers that show it.
- **Deletions,** in the worker: `devices.home_deletions` revokes a deleted home's devices and forgets its challenges and first answers; `devices.account_deletions` forgets what a deleted account asked for. Neither holds a lock: each deletes the challenges first, so that a registration racing it either ends first, and what it added goes too, or finds its challenge gone. Tests run both orders, for a home and for an account.
- **Shared:** the app API's conventions move from `accounts` to `shared/app_api.py`, since two modules serve the API: bodies, identifiers, pages, bearer tokens, Idempotency-Keys and problems. `[app_api] idempotency_retention` is the setting both read. `Accounts.membership` tells the other modules what an account is in a home.
- **`connected`** is false: no device connects before the cloud link's control channel. `kind`, `model` and `software` come with its `hello`.
- **Review:** of 82 mutants of the rules, 81 failed the tests at first. The other showed a missing test: a deleted home's first answers that show no device, such as a refusal's, went with it only by a statement that no test needed, since the others went with their devices. A test now holds it, and the mutant fails it.
  - **A worker that logged every event:** the revocation's log line came for a home with no devices too, which `tests/test_main.py` caught in the worker's own process. It now logs what it revoked only.
  - **A lock that did nothing:** the home's deletion first held the home, as a registration does. Its challenges, deleted first, already order the two, so it holds nothing now.
  - The review checklist gains what these met: values read from a token before it is verified, keys read one way only, deletions that cannot lock another module's rows, and handlers that log what they changed.

**Decisions:** delegated to the assistant, as the owner chose on 2026-11-03 for long-term development: all of [ADR-0010](../decisions/0010-device-registrations.md), and:
- **the steps,** each one whole: this one; then the token endpoint; then the control channel's session, with `hello`, `connected` and `bye` `revoked`. Revoking a deleted home's devices comes now rather than with the tokens, so that no device stays in a deleted home, where it would be `device_taken` elsewhere and kept past its home (PRIV-4);

## 2026-11-09 — Devices: the token endpoint

**Done:** `/device/token`, the cloud link 3.0's token endpoint, the second of the devices' three steps. A device proves who it is with an assertion that its key signs (RFC 7523, 2.2), and gets an access token.
- **The assertion:** its header names the key's thumbprint as `kid`, which `devices.keys` finds. Then come its ES256 signature with that key; `aud`, the server the device was registered with, without a trailing slash, then `/device/token`; `iat`, `exp` and `nbf` within `[tokens] leeway`; `exp` at most 5 minutes after `iat`; `iss` and `sub` naming the key's device; and `client_id`, if it comes, naming it too.
- **Once only:** each `jti` is kept in Redis, for each device, until its assertion could no longer be valid, and a second use is refused. Two requests with one assertion get one token.
- **Refusals:** `invalid_client` (401) only for a key the cloud does not hold: never registered, removed, or gone with its home. The device then offers set-up. Any other failure is `invalid_request`, after which the device tries again later. Over `[devices.token_rate]`, 60 a minute for each address, the answer is 429 with `Retry-After`.
- **The access token:** the cloud's own JWT, as the app's (RFC 9068): `at+jwt`, its audience `device`, so that neither an app's nor a device's passes for the other. `sub` and `client_id` name the device; `[devices] access_lifetime` is 600 s.
- **Shared:** OAuth's form and errors move from the accounts' routes to `shared/oauth.py`, which both token endpoints use. A device identifier is read in one place for registrations and assertions.
- **Review:** PyJWT reads a NumericDate with `int()`, so `"iat": "1700000000"` or `true` passed its checks, and arithmetic on them would have failed as a 500. The assertion's times are now checked as JSON numbers. A request with an assertion and another credential, a `client_secret` or an `Authorization` header, is refused (RFC 6749, 2.3). Refusals are logged with their reason, never the assertion, but not those over the rate, which a flood would multiply.
- **Mutants:** all 40 mutants of the new rules fail the tests. Three needed a test of their own first: an assertion of five minutes exactly, a server with a trailing slash, and an unknown key while another device is registered.

**Decisions:** delegated to the assistant, as the owner chose on 2026-11-03:
- **`invalid_client` for unknown keys only.** RFC 7523, 3.2, gives it to every client JWT that fails, but the cloud link has the device offer set-up after it: a clock far off would then unbind a device. The cloud link lets any other code stand for "try again later", and `invalid_request` says that the request, not the device, was wrong.
- **The used `jti` in Redis,** as the sign-in's nonces are (ADR-0008, decision 3): losing them reopens, for 5 minutes at most, the replay of an assertion copied in that time, which TLS already keeps from others.
- **A limit for each address,** before any work: it bounds what anyone can make the cloud do, and lets a home's devices, behind one address, get their tokens together after an outage.
- **The registry alone decides:** a device whose key the cloud holds gets a token. A deleted home's keys go with the worker's consumer, within a second normally. A token issued just as its device is removed is refused when it opens the control channel, which checks the registry too.

**Problems / unfinished:**
- **Nothing reads the tokens yet:** the control channel, the next step, checks them, and the registry, at its handshake.
- **For ai-platform:** the cloud link could name the code for an assertion that fails while its key is known, which RFC 7523 would make `invalid_client`, and say that the endpoint may answer 429.

**Next:** the control channel's session: `hello`, `connected`, and `bye` `revoked`.

## 2026-11-11 — Devices: the control channel's session

**Done:** the cloud link 3.0's control channel, `/device/v3/link`, the third of the devices' steps: a device connects, says what it is, and is told when it is replaced or revoked. [ADR-0011](../decisions/0011-control-channels.md) says how the replicas share it.
- **The handshake:** the device's access token, then the registry. A device removed, gone with its home, or registered again since its token, gets 401 as Problem Details, and a replica going away 503.
- **The hellos:** the device's comes first, and the registry keeps its kind, model and software, which the app API's devices now show. The cloud answers with a new session, its time and `ping_interval`, without conversations or events yet. Another major gets `bye` `unsupported_protocol`; a first message that is no hello, or none in `hello_timeout`, `bye` `no_hello`. A conversation the device names, which the cloud does not hold, ends `lost`.
- **The session:** pings get pongs with the last number taken; numbers are checked (a duplicate is ignored, a skip ends the session `out_of_sequence`); a message that fails the schema gets `invalid_message`; a conversation request gets `unavailable`; what the cloud does not take yet is ignored. The cloud reads `rate` messages a second from a device, pings included, `burst` at once, with `backlog` waiting their turn, and tells it once when it drops some. A connection silent for two ping intervals closes, and so does one to which nothing could be sent for as long; a message over 1 MiB closes it too.
- **Presence and hints:** `connected` reads the presence in Redis, which names each device's newest connection. A newer connection, a removal and a home's deletion send a hint, which every replica hears; each also checks its connections every `check_interval`, against the registry and the presence, so that a lost hint delays a `bye` and never loses one.
- **Going away:** before uvicorn closes the WebSockets, the api sends `reconnect` on each session.
- **The example** `devices.json` runs whole, with a robot of the tests' own that connects and is told it is removed where the example says, against uvicorn on a port of the machine.

- **Second review:**
  - **What a device sent could crash its own session.** A `type` that is a list or an object raised `TypeError` where the cloud looked it up, and JSON nested some ten thousand deep raised `RecursionError` (11,331 on Windows). **Decisions:** delegated to the assistant, as the owner chose on 2026-11-03: all of [ADR-0011](../decisions/0011-control-channels.md), and:
- **the steps:** this one; then resuming sessions, with their state in Redis so that another replica takes them; then `update_required`, and 410 for a retired major, with `updates`;
- **a deleted home's devices:** the second review of the token endpoint found that they keep getting tokens until the worker's consumer runs, and so connect. The channel does not ask the accounts at its handshake: the registry alone decides, as at the token endpoint, so that the two never disagree; such a check would only cover connections opened within the lag, while devices stay connected; and every module's data of a deleted home lags as long (ADR-0011, decision 9);
- **two reasons the cloud link leaves open:** a first message that is no hello the cloud can read ends the session with `no_hello`, as the robot ends one whose cloud's hello it cannot read; a ping the cloud cannot read, with `error`, the reason a side takes for one it does not know. A device acts the same on either;
- **what the cloud cannot read** (second review): numbers past a double are left out, as I-JSON leaves them out (RFC 7493, 2.2), and so is nesting deeper than `max_json_depth`, as RFC 8259 lets a reader limit it (section 9). In a session, such a frame is ignored, for it has no number to answer. A failure of the cloud's own ends the session with `bye` `error` and 1011, RFC 6455's unexpected condition;
- **the shutdown's bound,** 3 s after `close_timeout`, so that a stop fits within the 10 s that Docker Compose waits by default (`stop_grace_period`, docs.docker.com, read 2026-11-12). uvicorn calls it `--timeout-graceful-shutdown` (uvicorn.dev/settings).
- **the depth of JSON** (CI of the second review): Python's reader fails 11,331 levels deep on Windows and reads 20,000 on Linux, where the C stack sets it, so a test that expected a refusal failed on CI. The depth is a setting now, `[app_api] max_json_depth` for the app API's bodies and `[devices.link] max_json_depth` for a device's messages, 64 in both (.NET's `JsonReaderOptions.MaxDepth` default, learn.microsoft.com, read 2026-05-27; the bodies and messages nest a few levels). `read_json` walks the parsed value level by level, without recursion; `RecursionError` stays caught for what Python's reader cannot follow.
