## 2026-11-01 — Signing in, the cloud's side

**Done:** the `accounts` module, which serves ai-platform's app API 1.0, Apple aside, on [ADR-0008](../decisions/0008-data-and-tokens.md)'s libraries.
- **Signing in:** a nonce in Redis, used once and limited for each address; the ID token checked against its provider's published keys, which are kept as long as the provider's caching headers say; the token exchange.
- **Sessions:**
  - access tokens are JWTs as RFC 9068 profiles them, signed with ES256 by keys that `ai-cloud signing-key` makes;
  - refresh tokens rotate on every use, and are kept as their SHA-256; one used twice ends its session;
  - each request checks that its session still exists, so ending a session or deleting the account stops its access tokens at once.
- **The account:** reading it and changing it with an ETag; linking and removing identities; listing sessions in pages and ending them; deleting the account after a fresh sign-in.
- **Development:**
  - a provider that signs test people in, on in the development environment only;
  - PostgreSQL 18 and Redis 8 in `deploy/compose.development.yaml`, whose images the tests run too.
- **Shared:** secrets from the environment or from files; the database and Redis; rate limits (GCRA, in Redis); JOSE; the protocols' schemas, read from `platform/`; Problem Details; a limit on request bodies.
- **Migrations:** one Alembic environment with a branch for each module, run by `ai-cloud migrate`, which can also write a module's next migration.
- **Review:** the locks are taken in one order (the account, its sessions, their tokens), so that no sign-in or refresh deadlocks with a deletion. Mutants of the main rules, and of the import contracts, all failed the checks.

**Problems / unfinished:**
- **Apple:**
  - its ID tokens;
  - its authorization code, exchanged for its refresh token, which is kept encrypted;
  - revoking that token when the identity or the account goes.

  Apple gives the person's name to the app only, so the app API needs a field for the app to pass it on: a minor version.
- `owns_home_with_members` comes with homes.
- **Behind a reverse proxy,** `[api] forwarded_allow_ips` must name it, or every request counts as the proxy's for the nonces' rate. The production deployment, not written yet, must set it.
- **For ai-platform:**
  - the app API does not say which status a refused ID token gets when it links an identity; the cloud answers 403;
  - its schema allows control characters in names, which the cloud refuses.
- **Not swept yet:** sessions left unused by accounts that never sign in again. That is the `worker`'s job, once it exists.

**Next:**
- Apple, once there is an Apple developer account.
- ai-app's `account` module, against the development cloud.
- ai-platform: mark the app API's cloud side implemented.

The app API defines them in a later minor version, in ai-platform first. `owns_home_with_members` waits for them.
- **The `worker` process**, to deliver the events, delete across modules and sweep idle sessions.
- **Security events for the owner:** a new sign-in, or a refresh token used twice, should reach the owner (`notifications`) and the operators (`operations`). Today they are only logged.

**Next:** In ai-platform, the app API's homes and members, as a minor version. Then homes in `accounts`, and the outbox with the `worker`, before `devices`.

## 2026-11-03 — Homes, the cloud's side

**Done:** `accounts` serves ai-platform's app API 1.1, but for the page at `/join`, on [ai-platform ADR-0009](https://github.com/trungnguyen278/ai-platform/blob/main/docs/decisions/0009-people-in-a-home.md). `platform/` moves to `app/v1.1`.
- **Homes:** creating, reading and changing them; handing one over and deleting it, after a fresh sign-in.
- **People:** the owner, admins, members and profiles, in one table with one identifier; names that are each home's; what each role may do. A home the account is not in answers `404`, as if it did not exist.
- **Invitations:** a code that works once, kept as its SHA-256; looking before agreeing; a retry after a lost answer ends in the same place.
- **Deleting an account** now stops with `owns_home_with_members`, or takes along a home whose other people are all profiles, and removes its person from the homes it does not own.
- **`Idempotency-Key`:** the first answer is kept in the request's own transaction, so that a change and its answer stand or fall together. A failed request keeps nothing. An advisory lock tells a retry that the first request still runs.
- **Locks:** an account, then a home, then what is in the home. Whatever changes a home holds it, so its limits and its one owner hold under races, and tests run those races.
- **Time zones:** the `tzdata` package (2026.6, 2026-10-28, Apache-2.0, read from PyPI), so that a name is good on every host. The list comes from the package and not from `available_timezones`, which adds what the host has, such as `localtime`.
- **Structure:** `routes` and `service` are packages now, since homes would have doubled them.
- **Tests:** the specification's `homes.json` runs from beginning to end against the api. `protocol_schema` now makes one schema for each definition: checking the whole file against JSON Schema's own takes some 70 ms, and doing it for every answer the tests read took CI to eleven minutes.
- **Review:** it found three things, which tests now hold. 33 mutants of the main rules all failed the tests.
  - **Patterns:** Python's `$` also matches before a last newline, so `"vi\n"` passed the schema, for every protocol. `shared/protocols.py` now reads `$` as JSON Schema means it. Classes such as `\d`, `\w` and `\s` differ too, measured against Node: only the email's pattern uses one, its `\s`, on which the two disagree for six characters that have no place in an address. A test lists the patterns that use one.
  - **Text:** a lone surrogate, which JSON's escapes can spell, reached PostgreSQL's driver and failed as a `500`, at the account's name too. It now answers `400`.
  - **A deadlock:** deleting old first answers at the start of a request held their rows before the home, while removing a person holds them in the other order. A request now touches none but the one its key replaces.

**Decisions:** The owner accepted ai-platform's ADR-0009, and chose to build the whole of the app API 1.1 at once, so the [architecture](../architecture.md#phases)'s phases changed.

**Problems / unfinished:**
- **`/join` and the files that let a link open the app** are not served yet. The page is the first text the cloud shows people, which comes from a catalog, and [ai-platform ADR-0007](https://github.com/trungnguyen278/ai-platform/blob/main/docs/decisions/0007-catalogs.md) has MF2's Python library brought up to the specification before the cloud uses catalogs. The files also need the project's domain, and the app's signing keys. Until then, the app can share a link for people to paste.
- **Domain events:** removing a person or deleting a home deletes only the accounts' own rows, and a home's devices are not revoked yet. No other module holds anything yet, and `devices` comes after the outbox.
- **Not swept yet:** first answers older than their retention, which a retry ignores and which go with their person. That is the `worker`'s job, as for idle sessions.
- **For ai-platform:** the email's pattern should spell its class out, and its CI keep every pattern to what Python and ECMA-262 read alike.
- **For ai-robot:** its `core/data.py` also checks with jsonschema, with Python's `$`.

## 2026-11-04 — The app API 1.3: refreshing again after a lost answer

**Done:** `platform/` moves to `app/v1.3`, and the cloud implements it ([ai-platform ADR-0011](https://github.com/trungnguyen278/ai-platform/blob/main/docs/decisions/0011-refreshing-again.md)).
- **A refresh token now records the token it replaced** (`replaces`, migration `accounts_0003`).
- **A used token refreshes again** when the session's current token replaced it, and its first use is within `refresh_reuse`, 60 seconds. The current token is then marked used, so that whoever presents it ends the session.
- **Two refreshes with one token** both succeed now: the second waits for the first, then counts as a retry. Only the later answer's token works.
- **Tests:** retries, more than one of them, the window, the lost answer's token, `refresh_reuse = 0`. Five mutants of the rule all failed them.

**Decisions:** delegated, as in ai-platform's entry of the same day. The rule follows the token's replacement, not only the time: a replacement that was used, or a token two steps back, still ends the session.

**Next:** ai-platform says that the cloud implements 1.3. Then ai-app's `account`, whose session retries a refresh only after no answer came.

## 2026-11-05 — Domain events, and the `worker`

**Done:** [ADR-0009](../decisions/0009-domain-events.md), and what it decides: an outbox in each module, the `worker` process that relays it to Redis Streams and hands the events to their consumers, and the accounts' first events.
- **Writing:** `accounts.outbox` (migration `accounts_0004`), which the accounts' transactions write through their `emit`, beside their change. `shared/events` declares an outbox for any module.
- **Relaying:** the worker polls every 0.5 s.
  - One relay at a time numbers each outbox's new events, under an advisory lock.
  - Each event goes to `<module>:events` with its place as its entry's identifier. So nothing is written twice, and what Redis lost, or a crash left out, is written again from the outbox.
  - Events stay 7 days in the outbox and the stream once relayed.
- **Consuming:** a consumer is a consumer group that reads from the start of the stream.
  - An event whose handler fails is tried again after 30 s, then after twice as long each time, up to 6 hours.
  - After 20 deliveries it goes to its module's dead letters, with an error in the log.
- **The accounts' events:** `accounts.member.removed.v1`, `accounts.home.deleted.v1` and `accounts.account.deleted.v1`. Deleting an account writes the events of the homes it leaves and takes along, then its own.
- **The process:** `ai-cloud worker`, with an `[events]` table in the configuration. It stops on SIGINT and SIGTERM, and on Ctrl+Break on Windows, which the tests send to a real process.
- **Tests:** against PostgreSQL and Redis, as before, which CI already starts.
- **Review:**
  - **Text:** a lone surrogate in an event's data, which a `json` column takes as an escape, would have stopped its outbox for good: Redis's client cannot encode it. An event's data now travels as ASCII JSON.
  - **Sweeps:** two workers could have swept the same rows at once. A sweep now takes the outbox's turn, as the numbering does.
  - **Tests:** the backoff test kept margins of 200 ms, thin for a busy CI machine. They are now half of each delay.
  - **Mutants:** of 44 mutants of the rules, 41 failed the tests at first. The other three showed a bug and two missing tests:
    - **A restored outbox:** the relay checked for a stream past its outbox after the round had numbered. After PostgreSQL is restored from a backup, the outbox could thus give a place again that the stream still held. Redis would refuse that event as already there, and it would be lost. The check now runs under the outbox's turn, before any place is given.
    - Nothing showed that the relay rests only when there is nothing more, nor that a consumer asks Redis for an event only once its delay has passed.

    Tests now hold all three, and the first fails on the code before the fix. The three mutants, and two more of the moved check, now fail them too.
  - The review checklist gains a section on domain events.

**Decisions:** delegated to the assistant, as the owner chose on 2026-11-03 for long-term development: all of ADR-0009.
- An outbox in each module, not one for the cloud, so that a module can still move to a database of its own.
- Polling, without LISTEN/NOTIFY, which PgBouncer's transaction pooling cannot carry, and which serializes commits.
- Places from the outbox as the stream's identifiers, rather than Redis's idempotent XADD, which remembers for a day at most.
- A growing delay between tries, so that an outage of a day or two puts nothing aside.
- No reverse-DNS prefix on the types, since the events stay in the cloud.

**Problems / unfinished:**
- **No module consumes yet.** `devices` will revoke a deleted home's devices.
- **An event about a deleted account** keeps its identifiers, and nothing else, for the retention: ADR-0006 should say so.
- **The worker's container and health check** come with the production deployment, which is not written yet.
- **Not swept yet:** idle sessions, and old first answers. They are schedules, the worker's other work.

**Next:** `devices` and set-up's registration into a home, which consumes `accounts.home.deleted.v1`. Then the worker's schedules.
